# SmallLLM-DPO

**Does DPO Alignment Improve Function Calling in Small LLMs?**

*Spoiler: Not with synthetic preference data — and the ablation studies explain why.*

## TL;DR

We apply DPO (Direct Preference Optimization) with QLoRA to Qwen2.5-3B-Instruct for function calling alignment. Through systematic ablation studies, we find that **synthetic preference data provides no meaningful improvement** over the already-strong base model — and we show exactly why through beta and data scaling experiments.

> **Key insight**: When the base model already excels (93% JSON validity), the bottleneck for DPO is **data quality**, not training method. Programmatically injected errors are too artificial — the model never makes these mistakes in the first place.

## Why DPO Didn't Work (Analysis)

```
                    What we expected           What actually happened
                    ┌──────────────┐           ┌──────────────────────┐
Preference Data ──> │ DPO learns   │     ──>   │ Base model already   │
(chosen/rejected)   │ to avoid     │           │ avoids these errors  │
                    │ these errors │           │ → no signal to learn │
                    └──────────────┘           └──────────────────────┘
```

Three converging pieces of evidence:

1. **Beta analysis**: Higher beta (stronger KL constraint) = better results. This means the DPO loss is pulling the model *away* from good behavior, and the KL term is the only thing holding it back.

2. **Data scaling**: Performance *decreases* with more data (92% → 83%). The preference pairs contain more noise than learning signal — programmatic error injection creates errors the model would never naturally produce.

3. **Judge evaluation**: 90% tie rate confirms Base and DPO are functionally equivalent. DPO training is effectively a no-op at best.

**Root cause**: Our rejected samples are generated by programmatic error injection (`_create_malformed_value()`). These synthetic errors — corrupted JSON values, swapped argument types — are too artificial. The Qwen2.5-3B-Instruct model, already trained on massive instruction data, never makes these mistakes. DPO has nothing useful to learn.

## Future Work: On-Policy Data Generation

The most promising path to making DPO effective here:

```
Current (off-policy):                    Proposed (on-policy):
                                         
DeepSeek generates ──→ artificial        Qwen generates ──→ real model
both chosen and        errors that       multiple responses  mistakes
rejected               model never                          │
                       makes             DeepSeek judges ───┘
                                         best → chosen
                                         worst → rejected
```

The infrastructure already exists in `sampler.py` and `judge.py` — the main change is in the data generation pipeline (Notebook 01).
